## What was built

```
operaton/
  bpmn/statutory-audit.bpmn   engagement lifecycle: 6 phases, 6 gates,
                              partner-approval user tasks with forms,
                              PBC-chase repeating boundary timer,
                              non-interrupting deadline-watch sub-process
  bpmn/audit-step.bpmn        one programme step, multi-instance child process
  sql/001_bridge_schema.sql   orchestrator.* schema — creates nothing in
                              workflow.*; orchestrator.v_steps is the seeded
                              registry contract to repoint later
  workers/*.py                fetch-and-lock worker (5 topics) + one-way
                              mirror; handlers raise incidents rather than
                              faking success when unconfigured
  scripts/, Makefile, docker-compose.yml, .env.example
  docs/architecture.md        ADR: why this split, why steps stay data, risks,
                              alternatives, rollout
```

Central design decision, stated as a rule in both the code comments and the
README: **the 31-step programme is not modeled in BPMN.** It is read as data
by the multi-instance call activity. Adding a step must remain an `INSERT`,
never a redeploy + instance migration on a live engagement.

## Verification actually performed

Docker daemon came up in-container but `docker pull operaton/operaton` hit a
403 from `production.cloudfront.docker.com` — egress policy blocked it, not
retried or routed around. So nothing ran against a live engine. Compensated:

- Both BPMN files parsed and checked programmatically — every flow node has a
  `BPMNShape`, every sequence flow a `BPMNEdge`, all refs resolve, exclusive
  gateways with conditions all have a default flow. Fixed an actual bug this
  caught: XML comments containing `--` (section divider style) broke parsing.
- Started a real local PostgreSQL 16 server (`/var/tmp`, not the scratchpad —
  hit a socket permission error there first). Applied `001_bridge_schema.sql`
  twice to confirm idempotency (clean `NOTICE...skipping` on the second run).
- Seeded step results and ran `mirror.py`'s actual query functions
  (`step_counts`, `pending_steps`) against that database, then rendered
  `blocked_reason` — output was byte-identical to the live card format:
  `G-WP-CONCLUDED open, G-EVIDENCE-LOCK open · next: fw-je, fw-rp`.
- Unit-checked `derive_status`, gate predicates, variable encode/decode
  (`json_list_var` → `java.util.ArrayList` shape), and confirmed
  `sanctions_check` raises `NotConfigured` rather than returning a pass.

README states plainly what was and wasn't verified, and that the first
`make up && make deploy` against a real engine is the actual smoke test.
